# PRIFF-HMS Agent Rules

Current Mode: BUILD MODE (the only mode currently defined/used in this repo)

## Payroll Engine — do not touch without consultation

The Payroll Engine (payroll calculation logic: daily/monthly wage, OT 1.5/2/3,
ประกันสังคม, advance-payment deduction, absence deduction, withholding tax) was
designed in detail against Thai labor law 2026 (see `docs/payroll-architecture.md`
and `docs/payroll-database-design.md`). Do NOT modify any existing payroll
calculation logic, formulas, or the tables/functions that implement them, without
first raising it explicitly with the owner and getting a clear go-ahead. This
applies even to changes that look like small bug fixes — flag them instead of
silently "fixing" them. Read-only queries against this schema (e.g. ESS features
that display payslip/leave/attendance data) are fine and do not require approval.

Agent MAY (Authorized to auto-fix without approval):
- Fix syntax errors, build errors, lint errors, and import errors
- Fix SQL syntax errors, SQL formatting, ambiguous column references, and invalid SQL statements
- Refactor code and update HTML/JS/CSS files
- Create documentation and local test files
- Create new database tables/RLS policies for NON-payroll-engine features (e.g. ESS
  self-service features), provided schema-shaping decisions (which fields, what
  eligibility rule, how a limit is computed, etc.) are confirmed with the owner first
  via a direct question in the conversation before the migration is written. A
  separate formal ticket/sign-off step is not required in practice - asking the
  question and getting an explicit reply in-chat is sufficient approval.
- Commit, push, open a PR, and merge it into `main` without asking permission each
  time. Vercel auto-deploys `main` to production, so merging IS deploying - do it
  freely once Staging verification (below) passes, per the owner's standing
  instruction. No separate "should I deploy?" question is needed.

### Payroll Engine continuation workflow

For every Payroll Engine task, the agent must keep the owner oriented and advance the
work in a predictable order:

1. Read `database/MIGRATIONS_INDEX.md`, the payroll architecture docs, and the current
   Payroll UI/data flow before deciding what remains.
2. Separate work into: completed and verified, safe follow-up work, and calculation/
   legal decisions that still require owner sign-off.
3. After completing a payroll unit, report the completed step, its verification
   result, the current milestone, and the next numbered step. If the next step is
   within the already approved scope and does not change payroll formulas, legal
   interpretation, schema/security boundaries, or Production data, continue
   automatically instead of waiting for another prompt.
4. Before changing a formula or payroll calculation source (including paid OT hours,
   break-time treatment, absence deduction, SSO, tax, advances, or pay-frequency
   filtering), show the current behavior, proposed rule, affected examples, and
   targeted Staging tests, then obtain explicit owner approval in chat.
5. Demo and verification data must use `DEMO*` employees only. A payroll demo script
   must refuse to run if its selected period could include a non-demo employee, and
   it must print the generated period, run, employee count, and net total.
6. Never describe a Payroll Engine milestone as complete solely because the UI
   renders. Completion requires a non-zero DEMO payroll run on Staging, line-detail
   verification, approval-state verification where applicable, and a concise list of
   known deferred calculation decisions.

Agent MUST NOT (requires an explicit, in-chat go-ahead from the owner before proceeding):
- Modify any Payroll Engine calculation logic (see section above)
- Change RLS policy security architecture or Auth models in a way that alters who can
  see/do what (as opposed to fixing an obvious RLS gap/bug uncovered while building an
  approved feature - flag those as found, fix them, and say so plainly in the summary)
- Execute queries directly against the Production database for anything other than
  read-only verification (e.g. confirming a deploy went out)
- Delete core project data or files (test/demo data created by the agent itself for
  verification is fine to delete after use - see cleanup rule below)

Agent SHOULD:
- Work autonomously until builds, linter checks, and SQL syntax validations pass
  100%. That is the floor, not the ceiling - beyond it, scale additional
  verification (e.g. browser testing, exhaustive edge-case checks) to the actual
  risk of the change, per the Token/credit efficiency section below. Do not spend
  extra verification effort that doesn't materially increase confidence.
- Report ONLY when encountering unresolvable blockers, architecture changes, or a
  Payroll-Engine-adjacent question that needs owner input
- When uncertain about a low-risk implementation detail (naming, minor UI wording,
  which existing helper/pattern to reuse, etc.), make a reasonable assumption,
  state it clearly in the summary, and proceed instead of stopping to ask. Only
  interrupt the owner for a decision that touches Security/RLS/Auth, the Payroll
  Engine, legal/compliance interpretation (e.g. labor-law leave rules), schema/
  architecture design, or Production data - i.e. the same areas already called out
  under "Agent MUST NOT" above.

## Environments

- **Staging**: Supabase project `hcyibcqojsyldiyzperr.supabase.co`. All new migrations
  are written to `database/NN_description.sql` (idempotent: `CREATE ... IF NOT EXISTS`,
  `DROP POLICY IF EXISTS` before `CREATE POLICY`), applied here first via
  `node scripts/run-ess-migrations.js` (add the new file to the list near the top of
  that script), and verified here before anything touches Production.
- **Production**: the `main` branch, auto-deployed by Vercel on merge. The agent may
  push schema changes to Production only as a real migration file merged through the
  normal PR flow - never by running ad-hoc SQL directly against the Production
  database.

## Migration files: never consolidate, always index

`database/NN_*.sql` files are an append-only history of changes already applied to a
real database (Staging, and eventually Production) with real data in it — same model
as Rails/Django/Prisma/Supabase CLI migrations. **This directory growing to 60, 100+
files by the end of the project is normal and expected, not a problem to "clean up" by
merging files together.** Do not consolidate, delete, or edit old migration files once
they've been applied — that would desync the file history from what's actually been
run against the database, which is far worse than having many files.

The actual pain point as the count grows is *discoverability*, not file count. That is
solved by `database/MIGRATIONS_INDEX.md` (auto-generated, one-line summary per file) —
**run `node scripts/generate-migrations-index.js` every time you add a new migration
file**, and check the index first instead of opening individual migration files to
figure out what's already been done. This convention works identically regardless of
which AI model/tool is doing the work, since it's implemented as a plain script + a
committed markdown file, not something that depends on any model's memory.

## Test/demo data

- Only use demo accounts whose emp_id starts with `DEMO` (e.g. DEMO001, DEMOADMIN,
  DEMOSUP) for any live/browser verification. Never use real employee data or real
  credentials for testing.
- Temporary helper scripts written purely to set up/verify/tear down a test scenario
  belong in `scripts/_tmp_*.js` and must be deleted before committing. Any temporary
  test rows inserted into Staging tables during verification should be cleaned up
  afterward too, unless they're reusable demo accounts (those are fine to keep).

Notes and safe-guards:
- Any schema-altering change (DDL that adds/drops tables or changes data model semantics) must be confirmed with the owner (an in-chat question is sufficient - see above) and should be reflected in the relevant design doc if one exists.
- Any RLS or auth-related policy change that affects security boundaries requires an explicit go-ahead, except for fixing a clear pre-existing RLS gap/bug found while building an approved feature (fix it, disclose it clearly).
- All automatic fixes must be reversible (keep backups or create git commits with clear messages and the Co-authored-by trailer).
- Do not run or apply any migration to Production directly; migrations reach Production only via a merged PR after being validated on Staging.

## Token/credit efficiency (default behavior for this repo)

The owner explicitly asked to reduce unnecessary token usage without losing quality or
correctness. This section was tightened after a real cost review of a session that burned
~$218 in metered usage over 2 days (see git history / session notes around Aug 2026 for the
full self-audit). Unless the user says otherwise in a given message, default to the following:

- **Reporting style: concise by default.** Summarize what changed, what was verified,
  and what's next in a short list. Do not narrate every intermediate step or explain
  routine tool calls. Give full step-by-step detail only when: the user asks for it,
  the change is schema/RLS/security-related (per rules above), or something
  unexpected/risky was found.

- **Verification hierarchy — cheapest sufficient method first, always:**
  1. **SQL query / Node script against the DB directly** — for anything about data,
     schema, RLS policy correctness, or calculation logic. Cheapest and most precise.
  2. **`node scripts/rest-check.js "<table_or_rpc>?<query>"`** — for anything about
     whether the **Supabase REST/PostgREST layer** behaves correctly (embed
     relationships like `.select('*, employees(...))`, RPC calls, schema-cache
     errors such as "Could not find a relationship..."). This proves the exact same
     fact a browser test would, in one HTTP call, with no login/navigation/render
     overhead. **Do not open a full Playwright browser session just to prove a
     backend/data-layer fix works** — that was a real mistake made in a past
     session (proving an FK/schema-cache fix by logging into the UI and clicking
     through 3 pages, when one `rest-check.js` call proved the identical fact).
  3. **Full browser walkthrough (Playwright: navigate/click/screenshot)** — reserved
     for genuinely UI/UX-dependent behavior that cannot be confirmed any other way:
     visual layout/theme, click-through navigation between pages, modal
     rendering, whether a button is actually clickable/visible, multi-step user
     flows. If the thing being tested would look identical to the user regardless
     of *how* it's implemented under the hood, it doesn't need a browser.
  - **Match verification depth to the risk of the change**, not to "test
    everything the same way by default": a text-label fix does not need the same
    verification depth as a payroll tax calculation change.
  - When genuinely unsure which tier applies, start at tier 1/2 and only escalate
    to tier 3 if real doubt remains after the cheaper check.

- **Batch test scenarios into one script.** A single test scenario (setup test data →
  run/verify → clean up) should be ONE script file with one `node` invocation, not three
  separate `tmp-*.js` files run across three separate tool calls. Reuse
  `scripts/rest-check.js` and the existing `scripts/lib/env.js` connection helper instead
  of re-deriving Postgres connection logic in every new scratch file.

- **Migrations: `scripts/run-ess-migrations.js` now tracks applied files** in
  `public._schema_migrations` (by filename + content checksum) and skips anything
  already applied. Running it normally after adding one new migration file is now
  cheap (only the new file executes). Use `--only <filename>` to run/re-run a single
  file while iterating on a fix (e.g. after a migration fails partway and gets
  corrected), and `--force-all` only if you genuinely need a full replay. Do not
  reintroduce a hardcoded "run everything from scratch every time" pattern.

- **Git/PR workflow: this repo merges every PR with squash-merge**, which means the
  local feature branch's commit history is never the same object as what lands on
  `main`. To avoid repeatedly hitting merge-conflict/divergence errors when opening
  the *next* PR from the same long-lived branch (this happened 3 times in one
  session before this rule existed):
  - **Immediately after a PR merges**, before writing any new code: run
    `git fetch origin main && git reset --hard origin/main` on the local branch
    (do this before making the next commit, not after hitting a conflict).
  - Do not keep layering new commits on top of a branch whose earlier commits were
    already squash-merged into `main` without first resyncing as above.

- **New chat vs. continuing the same thread — concrete thresholds, not just vibes:**
  - **Hard checkpoint: after every merged PR.** A merged PR is a natural, clean
    boundary (work is committed, deployed, and verified). At that point, proactively
    tell the user this is a good place to start a new chat for the *next* unit of
    work, unless the very next task is a tiny direct continuation of the same PR's
    scope (e.g. "also fix a typo in the thing we just merged").
  - **Numeric backstop:** if the current chat has already produced **3 or more
    merged PRs**, or has run past roughly **50 user-visible turns**, strongly
    recommend a new chat before starting the next major task even if it feels
    topically related — re-explaining accumulated context in a fresh chat is
    cheaper than continuing to reprocess a very long history on every turn. State
    this recommendation plainly (e.g. "this chat has grown quite long — want me to
    continue in a new chat for the next phase?") rather than silently deciding.
  - The user can always override and say "just continue here" — these are defaults,
    not hard stops.

- **The user can override any default above at any time** by saying so in their
  message (e.g. "show me on the browser too" or "explain in more detail this time")
  - per-message requests always take priority over these defaults.
