# PRIFF-HMS Agent Rules

Current Mode: BUILD MODE (the only mode currently defined/used in this repo)

## Payroll Engine — do not touch without consultation

The Payroll Engine (payroll calculation logic: daily/monthly wage, OT 1.5/2/3,
ประกันสังคม, advance-payment deduction, absence deduction, withholding tax) was
designed in detail against Thai labor law 2026 (see `docs/payroll-architecture.md`
and `docs/payroll-database-design.md`). Do NOT modify any existing payroll
calculation logic, formulas, or the tables/functions that implement them, without
first raising it explicitly with the owner and getting a clear go-ahead. This
applies even to changes that look like small bug fixes — flag them instead of
silently "fixing" them. Read-only queries against this schema (e.g. ESS features
that display payslip/leave/attendance data) are fine and do not require approval.

Agent MAY (Authorized to auto-fix without approval):
- Fix syntax errors, build errors, lint errors, and import errors
- Fix SQL syntax errors, SQL formatting, ambiguous column references, and invalid SQL statements
- Refactor code and update HTML/JS/CSS files
- Create documentation and local test files
- Create new database tables/RLS policies for NON-payroll-engine features (e.g. ESS
  self-service features), provided schema-shaping decisions (which fields, what
  eligibility rule, how a limit is computed, etc.) are confirmed with the owner first
  via a direct question in the conversation before the migration is written. A
  separate formal ticket/sign-off step is not required in practice - asking the
  question and getting an explicit reply in-chat is sufficient approval.
- Commit, push, open a PR, and merge it into `main` without asking permission each
  time. Vercel auto-deploys `main` to production, so merging IS deploying - do it
  freely once Staging verification (below) passes, per the owner's standing
  instruction. No separate "should I deploy?" question is needed.

Agent MUST NOT (requires an explicit, in-chat go-ahead from the owner before proceeding):
- Modify any Payroll Engine calculation logic (see section above)
- Change RLS policy security architecture or Auth models in a way that alters who can
  see/do what (as opposed to fixing an obvious RLS gap/bug uncovered while building an
  approved feature - flag those as found, fix them, and say so plainly in the summary)
- Execute queries directly against the Production database for anything other than
  read-only verification (e.g. confirming a deploy went out)
- Delete core project data or files (test/demo data created by the agent itself for
  verification is fine to delete after use - see cleanup rule below)

Agent SHOULD:
- Work autonomously until builds, linter checks, and SQL validations pass 100%
- Report ONLY when encountering unresolvable blockers, architecture changes, or a
  Payroll-Engine-adjacent question that needs owner input

## Environments

- **Staging**: Supabase project `hcyibcqojsyldiyzperr.supabase.co`. All new migrations
  are written to `database/NN_description.sql` (idempotent: `CREATE ... IF NOT EXISTS`,
  `DROP POLICY IF EXISTS` before `CREATE POLICY`), applied here first via
  `node scripts/run-ess-migrations.js`, and verified here before anything touches
  Production.
- **Production**: the `main` branch, auto-deployed by Vercel on merge. The agent may
  push schema changes to Production only as a real migration file merged through the
  normal PR flow - never by running ad-hoc SQL directly against the Production
  database.

## Test/demo data

- Only use demo accounts whose emp_id starts with `DEMO` (e.g. DEMO001, DEMOADMIN,
  DEMOSUP) for any live/browser verification. Never use real employee data or real
  credentials for testing.
- Temporary helper scripts written purely to set up/verify/tear down a test scenario
  belong in `scripts/_tmp_*.js` and must be deleted before committing. Any temporary
  test rows inserted into Staging tables during verification should be cleaned up
  afterward too, unless they're reusable demo accounts (those are fine to keep).

Notes and safe-guards:
- Any schema-altering change (DDL that adds/drops tables or changes data model semantics) must be confirmed with the owner (an in-chat question is sufficient - see above) and should be reflected in the relevant design doc if one exists.
- Any RLS or auth-related policy change that affects security boundaries requires an explicit go-ahead, except for fixing a clear pre-existing RLS gap/bug found while building an approved feature (fix it, disclose it clearly).
- All automatic fixes must be reversible (keep backups or create git commits with clear messages and the Co-authored-by trailer).
- Do not run or apply any migration to Production directly; migrations reach Production only via a merged PR after being validated on Staging.

## Token/credit efficiency (default behavior for this repo)

The owner explicitly asked to reduce unnecessary token usage without losing quality.
Unless the user says otherwise in a given message, default to the following:

- **Reporting style: concise by default.** Summarize what changed, what was verified,
  and what's next in a short list. Do not narrate every intermediate step or explain
  routine tool calls. Give full step-by-step detail only when: the user asks for it,
  the change is schema/RLS/security-related (per rules above), or something
  unexpected/risky was found.
- **Verification depth: match the risk of the change.**
  - Pure backend/logic changes (SQL migration behavior, RLS policy correctness,
    service-layer functions) → verify via SQL queries / Node scripts / logs. This is
    sufficient; do not also drive a full browser session by default.
  - Changes to visible UI/UX (new pages, layout, buttons, forms rendering) → a
    lightweight browser check is warranted since visual correctness can't be
    confirmed from SQL/logs alone.
  - If genuinely unsure which applies, do the cheaper check first (SQL/log) and only
    escalate to a full browser walkthrough if the cheaper check leaves real doubt.
- **The user can override either default at any time** by saying so in their message
  (e.g. "show me on the browser too" or "explain in more detail this time") - these
  per-message requests always take priority over the defaults above.
- **New chat vs. continuing the same thread:** prefer starting a new chat/session when
  the next task is largely unrelated to the current thread's context (e.g. moving from
  ESS features to an unrelated system). Continue in the same thread when the next task
  builds directly on what was just discussed/implemented, since re-explaining that
  context in a fresh chat costs more than continuing does. When unsure, ask the user.
