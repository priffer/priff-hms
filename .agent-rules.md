# PRIFF-HMS Agent Rules

Current Mode: BUILD MODE

Agent MAY (Authorized to auto-fix without approval):
- Fix syntax errors, build errors, lint errors, and import errors
- Fix SQL syntax errors, SQL formatting, ambiguous column references, and invalid SQL statements
- Refactor code and update HTML/JS/CSS files
- Create documentation and local test files

Agent MUST NOT (Requires explicit CEO/Architect approval):
- Add/remove tables or change database schema design
- Change RLS policy security architecture or Auth models
- Execute queries on Production Database
- Delete core project data or files

Agent SHOULD:
- Work autonomously until builds, linter checks, and SQL validations pass 100%
- Report ONLY when encountering unresolvable blockers or architecture changes

Notes and safe-guards:
- Any schema-altering change (DDL that adds/drops tables or changes data model semantics) must be approved and recorded in design documents and a formal ticket.
- Any RLS or auth-related policy change that affects security boundaries requires an explicit sign-off.
- All automatic fixes must be reversible (keep backups or create git commits with clear messages and the Co-authored-by trailer).
- Do not run or apply any migration to Production; test and validate on Staging only.

## Token/credit efficiency (default behavior for this repo)

The owner explicitly asked to reduce unnecessary token usage without losing quality.
Unless the user says otherwise in a given message, default to the following:

- **Reporting style: concise by default.** Summarize what changed, what was verified,
  and what's next in a short list. Do not narrate every intermediate step or explain
  routine tool calls. Give full step-by-step detail only when: the user asks for it,
  the change is schema/RLS/security-related (per rules above), or something
  unexpected/risky was found.
- **Verification depth: match the risk of the change.**
  - Pure backend/logic changes (SQL migration behavior, RLS policy correctness,
    service-layer functions) → verify via SQL queries / Node scripts / logs. This is
    sufficient; do not also drive a full browser session by default.
  - Changes to visible UI/UX (new pages, layout, buttons, forms rendering) → a
    lightweight browser check is warranted since visual correctness can't be
    confirmed from SQL/logs alone.
  - If genuinely unsure which applies, do the cheaper check first (SQL/log) and only
    escalate to a full browser walkthrough if the cheaper check leaves real doubt.
- **The user can override either default at any time** by saying so in their message
  (e.g. "show me on the browser too" or "explain in more detail this time") - these
  per-message requests always take priority over the defaults above.
- **New chat vs. continuing the same thread:** prefer starting a new chat/session when
  the next task is largely unrelated to the current thread's context (e.g. moving from
  ESS features to an unrelated system). Continue in the same thread when the next task
  builds directly on what was just discussed/implemented, since re-explaining that
  context in a fresh chat costs more than continuing does. When unsure, ask the user.
